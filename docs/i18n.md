# i18n: translatable fields + dashboard strings

Two separate things, both locale `en` (default) / `ar`:

1. **Translatable data fields** — a model column like `Post.title` that
   holds a different value per locale, stored in the database.
2. **UI strings** — static labels/buttons/toasts, never stored, resolved
   client-side from a dictionary.

`Post.title` demonstrates both together; see [reference-module.md](./reference-module.md)
for the rest of what Posts demonstrates.

## Translatable data fields

**Backend**

- The column is `json`, storing `{ "en": "...", "ar": "..." }`
  (`database/migrations/..._convert_posts_title_to_translatable.php`, which
  wraps any pre-existing string value as `{ "en": "<old value>" }` rather
  than discarding it).
- `App\Models\Post` casts it `'title' => 'array'` and mixes in
  `App\Support\HasTranslations`, which adds `->translate('title', $locale)`
  — resolves to that locale's value, or the default locale's if missing.
- `App\Http\Requests\Post\{Store,Update}PostRequest`: `title.en` is
  `required`, `title.ar` is `nullable` — only the default locale is
  mandatory, same pattern to follow for any other locale you add.
- `App\TypeScript\TranslatableText` (`{ en: string; ar: string | null }`)
  is the fixed-shape TS type generated for any translatable field — see
  `PostType::$title`. Fixed props (not a dynamic `Record<string,string>`)
  because the locale set here is fixed (`en`/`ar`); if that ever needs to be
  config-driven instead, this is the type that'd have to become a map.
- `App\Http\Resources\PostResource`: returns `title` as the full `{en,
  ar}` object by default (matches the generated type, and is what this
  app's own frontend consumes) — pass `?lang=en` or `?lang=ar` to instead
  get `title` back as that locale's single resolved string. That's for
  external API consumers (e.g. a mobile client that only wants one string
  and doesn't care about the object shape); this project's own frontend
  never sends `lang`.

**Frontend**

- `src/components/translatable-input.tsx` — `<TranslatableInput>`: a tab
  strip (one tab per locale) above a single text input, all locales' inputs
  mounted at once (switching tabs just toggles `hidden`, so nothing is lost
  by tabbing away), each input's `dir` following that locale's own writing
  direction. A tab gets a small dot if that locale's value is empty, and
  the default locale's tab is starred. Controlled: `value: Partial<Record<Locale,
  string>>` / `onChange`, same shape the API round-trips.
- Wire it into a form via `FormField` like any other field, but skip
  `<FormMessage>` — errors are per-locale, not one message, so they're
  passed as `errors={{ en: ..., ar: ... }}` instead and rendered under each
  locale's own input. See `title`'s `FormField` in `post-form.tsx`.
- `postSchema.title` (`src/lib/schemas.ts`) is `translatableTextSchema` —
  mirrors the backend's `title.en required / title.ar optional` split.
  Server-side errors come back keyed `title.en`/`title.ar`; list both
  (not `title`) in `applyServerErrors`'s `knownFields` — see
  [forms.md](./forms.md) for why that list has to be exhaustive.
- `src/lib/i18n/resolve.ts`'s `resolveTranslation(value, locale)` — the
  display-side equivalent of the backend's `translate()`, used wherever a
  translatable field needs to render as one string (the posts table's
  Title column, for instance).

**Adding a translatable field to a different model**

1. Migration: `json` column (wrap existing data instead of dropping it, if
   any — copy the `convert_posts_title_to_translatable` migration's shape).
2. Model: cast the column `'array'`, mix in `HasTranslations`.
3. Requests: `field.en` required, `field.<other locale>` nullable, for
   each locale.
4. TypeScript type: type the property `TranslatableText` (reuse it — don't
   redeclare the shape per field).
5. Resource: object by default; add the `?lang=` opt-in only if an external
   consumer actually needs it (skip it otherwise — Posts' Resource keeps it
   mostly to document the pattern).
6. Frontend: `<TranslatableInput>` in the form, `translatableTextSchema` in
   the zod schema, `resolveTranslation()` anywhere it's displayed as text.

## UI strings

- `src/lib/i18n/locales/{en,ar}.json` — one dictionary per locale, nested
  by feature (`posts.form.title`, `nav.logout`, ...). `src/contexts/i18n-context.tsx`'s
  `I18nProvider`/`useI18n()` (same shape as `AuthProvider`/`useAuth()` —
  see [layout.md](./layout.md)) exposes `t(key, vars?)`, which looks the
  key up in the active locale's dictionary and falls back to the default
  locale's if missing — a key never renders raw to the user, it renders in
  whichever locale actually has it.
- `t()` supports `{placeholder}` interpolation: `t("translatable.missing", { locale: "ar" })`.
- **Only Posts + `SiteHeader` are wired through `t()`** — the auth pages
  (login/register/forgot-password/reset-password), dashboard, and
  `/admin/users` still have hardcoded English strings. That's a deliberate
  scope cut, not a partial rollout gone stale: Posts is this repo's
  designated reference module (see [reference-module.md](./reference-module.md)),
  so it's where the full pattern — translatable field *and* translated UI
  — is demonstrated end to end. Copy the pattern into the other pages by
  adding their strings to both locale files and swapping in `t("...")`;
  there's nothing else to it.

## Locale resolution and persistence

- **Frontend**: `I18nProvider` reads `localStorage["locale"]` on load
  (defaulting to `en`). Switching locale (`LanguageSwitcher`, in
  `SiteHeader`) writes it back to `localStorage` immediately, and — only if
  a user is logged in — `PATCH`es `/api/user/locale` to persist it
  server-side too, best-effort (the UI has already switched either way).
  On first load, if `localStorage` had nothing set yet and the logged-in
  user has a saved `locale`, that's adopted instead of the `en` default.
  `<html lang>`/`dir` follow the active locale via `HtmlAttributesSync`
  (client-side, after mount — the root layout is a server component and
  can't hold this state itself, same reasoning as `next-themes` applying
  the `.dark` class post-mount; see [theming.md](./theming.md)).
- **Backend**: `apiFetch` (`src/lib/api.ts`) sends the frontend's current
  locale as `Accept-Language` on every request. `App\Http\Middleware\SetLocale`
  (registered globally in `bootstrap/app.php`) resolves the request locale
  — `?lang=` query param, then the authenticated user's saved `locale`
  column, then `Accept-Language`, then Laravel's configured default — and
  calls `App::setLocale()`, so anything reading the app locale (validation
  messages, in particular) responds in it.
- **Validation messages**: `lang/ar/validation.php` only overrides
  `attributes` (field display names) for `ar` — the actual rule phrasing
  ("required", "max", ...) isn't translated and falls back to Laravel's
  English default automatically (Laravel's translator falls back per-key,
  not per-file). Full validation-message translation, and translating
  notification/email content, are both out of scope here — same "documents
  the pattern, doesn't chase full coverage" tradeoff as the UI strings
  above.
